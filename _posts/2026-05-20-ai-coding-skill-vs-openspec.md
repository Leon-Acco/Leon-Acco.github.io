### 核心结论：Skill vs Spec（OpenSpec）

- **Skill**：可复用的“能力包 / SOP”。目标是让 AI 在合适场景按固定流程稳定执行。
- **Spec（OpenSpec）**：面向某一次变更/功能的“可审阅规格说明”。目标是先对齐再写代码，避免“vibe coding”。
- **最佳组合**：**Spec 管 What（本次要交付什么）**，**Skill 管 How（每次怎么做才稳）**。

---

### 什么时候用 Skill？

更适合这些情况：

1. **重复性强**：评审、重构、补测试、生成文档、release checklist。
2. **需要固定流程**：例如“先读规范 → 列影响面 → 实现 → 自检 → 总结”。
3. **需要节省上下文**：把流程/模板封装成按需加载的技能，减少每次 prompt 重复粘贴。
4. **跨项目复用**：同一套做事方法可以在多个仓库反复使用。

一句话判断：**“这事以后还会反复做，而且希望 AI 每次都按同一套 SOP 做” → 用 Skill。**

---

### 什么时候用 Spec（OpenSpec）？

更适合这些情况：

5. **需求容易跑偏 / 影响面大**：跨模块、多文件、行为语义会变。
6. **需要审阅对齐**：让“目标与验收”从聊天记录落到可复用文档。
7. **需要任务拆解并持续同步**：对齐后再实现，减少返工。
8. **更接近可维护的软件交付**：越工程化、越多人协作，Spec 越值。

一句话判断：**“这次变更复杂、容易误解、需要确认验收标准” → 用 Spec。**

---

### “我的代码风格 / 框架约束 / 异常标准”属于 Spec 还是 Skill？

结论：**更推荐放 Spec（项目级规范）**，然后用 Skill 去“执行/检查”。

- **代码风格与约定**：命名、目录结构、注释、分层约束。
- **异常抛出与错误码标准**：业务异常 vs 系统异常、错误码结构、对外信息、日志规则。
- **框架/架构约束**：允许/禁止的依赖方向、关键中间件与通用模式。

- **实现流程 Skill**：每次开发都强制“读规范 → 设计异常 → 写测试 → 自检”。
- **评审 Skill**：按“风格/架构/异常/可维护性/边界条件”清单化检查。
- **安全重构 Skill**：小步提交、每步验证、说明不变性。

---

### 你担心的点：Spec 写全量会很花时间

解决策略：**不写全量，只写最小可用 Spec（MVS）**。

9. 项目目标与边界（做什么，不做什么）
10. 架构骨架（分层与依赖方向）
11. 最在意的“红线”约定（3–5 条即可）
12. **异常与错误码标准（强烈建议写）**
13. 验证方式（怎么跑测试 / 怎么算通过）

   - **项目级 Spec（稳定，1 页以内）**：通用约束与红线。
   - **变更级 Spec（每个需求一份）**：目标、验收标准、任务拆解。

   - 做一个 **spec-writer** skill：通过固定的 3–5 个关键问题，自动产出“变更级 spec”，你只需要改关键句子。

---

### 先开始开发时，我建议准备哪些 Spec / Skills？

目标：**快速开发 + 可控**。

1) **项目级 Spec（稳定，1 页以内）**

- 技术栈与运行方式（启动、测试命令）
- 分层/依赖约束
- 3–5 条红线风格约定
- **异常与错误码标准**
- 提交与变更要求（是否必须测试、commit 规范）

2) **变更级 Spec（每次一个需求）**

- 目标与不做什么
- 验收标准（输入/输出/边界）
- 任务拆解（3–10 条）
- 风险点与回滚点（可选）

14. **spec-writer**：问关键问题并生成/补齐变更级 spec。
15. **task-breakdown**：影响面分析与任务拆解（哪些文件、怎么改、风险）。
16. **exception-policy-enforcer**：实现与评审时强制遵守异常/错误码/日志规范。
17. **test-required**：强制补齐单测或最小验证脚本，并输出测试清单。
18. **refactor-safely**：小步重构、每步验证、不变性说明。
19. **code-review**：清单化 review（风格/架构/异常/边界/性能/可维护性）。

### 工具选择建议（Claude / TRAE / Codex）

> 以“先把代码做出来 + 还能控住质量”为目标。

- **Claude（Claude Code 工作流）**：更适合“先把方法论跑通 + 强对齐 + 拆解/设计/边界讨论”。
- **Codex**：更适合“你的技能库成熟之后”，把 SOP 工程化、提升执行效率。
- **TRAE**：适合作为 IDE 侧的执行端（更顺手的索引、补丁应用、运行验证）。具体落地细节建议按你实际使用的版本与入口再细化。

---

### 今天就能用的起步配置（推荐）

- **Spec**：项目级 1 页 + 当前需求的变更级 1 份
- **Skills**：先做 3 个
    - spec-writer
    - exception-policy-enforcer
    - test-required
- **工具**：优先用 Claude 跑通流程；等 skills 稳定后用 Codex 提升执行效率
