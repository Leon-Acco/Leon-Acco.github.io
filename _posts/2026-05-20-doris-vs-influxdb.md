# （一）、评估背景  
##  现状说明  
 当前车辆原始数据统一存储在 Apache Doris（华为云） 中，核心表结构如下（简化）：  

```sql
CREATE TABLE tbox_raw_data_compressed (
   ts           DATETIME     NOT NULL,
   dev_code     VARCHAR(32)  NOT NULL,
   cmd          INT          NOT NULL,
   vin_code     VARCHAR(17),
   data         STRING       NOT NULL, -- Base64 压缩原始数据
   receive_date DATETIME     NOT NULL,
   source       TINYINT      NOT NULL
)
UNIQUE KEY (ts, dev_code, cmd)
PARTITION BY RANGE(ts)       -- 按周分区
DISTRIBUTED BY HASH(dev_code) BUCKETS 512;

```

该表用于承载 **车辆原始上报数据**，具备以下特征：

+ 数据量大、持续写入
+ 明显的时间序列特征（ts 为主轴）
+ 查询以时间范围、设备维度为主
+ `data` 字段为压缩原始载荷，不可直接分析

## 评估目标  
+ 评估是否有必要、是否可行将**原始车辆数据存储从 Doris 迁移或分层到 InfluxDB**，并重点对比：
+ **合理性**
+ **扩展性**
+ **稳定性**
+ **未来 2~3 年是否仍是业内主流 / 首选方案**



# (二)、 现有 Doris 方案分析（结合表结构）  
## 当前 Doris 表的实际定位  
`tbox_raw_data_compressed_new` 本质是一张 **原始时序数据明细表**，Doris 在当前架构中被当作 **时序数据存储引擎** 使用。

主要依据：

+ `ts` 为分区键，严格按时间组织
+ 查询主路径必然是：  
`dev_code + cmd + 时间范围`
+ `data` 为 Base64 压缩字段，无法参与分析
+ 分区粒度为“周”，明显为长期历史数据设计
+ 提供给页面的历史数据查询能力也是以时序形式提供的

## Doris 承载该类数据的合理性分析  
#### 优点
+ Doris 对 SQL 支持友好（直接适配 Mybatis-plus）
+ 能统一承载分析与查询
+ 运维体系已有、无新增组件（使用华为云的表格存储）

#### 局限与问题（结构性）
**OLAP 引擎并非为高频原始时序写入设计**
       - UNIQUE KEY + merge-on-read
       - 时间范围扫描存在读放大
2. **分区与 bucket 数量随时间线性增长**
       - 周级分区长期会导致元数据和运维复杂度上升
3. **Base64 原始数据无法在 Doris 中直接发挥 OLAP 价值**
       - 该表只能“存”，不能“算”
4. **dev_code 高基数导致分布与扩容敏感**
       - bucket 数难以动态调整
       - 长期存在扩容风险
5. **华为云表格存储问题频繁，时长出问题，需要解决和维护，同时在使用上，明显感觉其产品能力不足。**

结论：  
**Doris 能承载该表，但成本、复杂度和长期稳定性并不理想。**

# （三）、InfluxDB 方案分析（映射当前表结构）  
### 与当前表的天然匹配点  
| **Doris 表特征** | **InfluxDB 适配情况** |
| --- | --- |
| 时间主轴 ts | 原生时间序列模型 |
| dev_code 高基数 | Tag 维度 |
| cmd 指令类型 | Tag / Measurement |
| 原始数据 data | Field（字符串/二进制） |
| 时间范围查询 | 核心优势 |
| 长期历史数据 | 原生保留策略 |

结合当前表的存储结构和使用用途， InfluxDB 的数据模型 **天然匹配当前表的访问模式**。  

###  InfluxDB 承载该类数据的合理性  
#### 优点
+ 为高频时序写入设计
+ 时间范围 + 窗口聚合性能稳定
+ 内建数据保留策略（Retention Policy）
+ 更适合长期全量原始时序数据存储

#### 注意点
+ 不适合复杂 Join
+ 不适合作为统一分析数仓
+ 高基数 Tag 需经过合理建模与压测

# （四）、两种方案对比分析
### 4.1 合理性对比
| 维度 | Doris（现状） | InfluxDB |
| --- | --- | --- |
| 原始时序数据存储 | 可行，但非最优 | **最适合** |
| 高频写入 | 可承载 | **原生优势** |
| 时间范围查询 | 可用 | **性能更优** |
| 原始数据长期保留 | 成本高 | **更合理** |
| 原始数据解析前存储 | 不经济 | **适合** |
| 聚合/Join 分析 | **强项** | 不适合 |

---

### 4.2 扩展性对比
**Doris**

+ 更适合扩展分析能力
+ 扩展原始时序数据规模成本高
+ 分区、bucket 调整复杂

**InfluxDB**

+ 水平扩展更贴合时序写入
+ 保留策略、冷热数据管理更自然
+ 更适合作为“时间数据底座”

👉 **扩展性结论**：

+ 原始数据：InfluxDB 更优
+ 分析数据：Doris 更优

---

### 4.3 稳定性对比
| 维度 | Doris | InfluxDB |
| --- | --- | --- |
| 高写入稳定性 | 可控但成本高 | **设计目标** |
| 时间跨度增长 | 运维压力增大 | **影响较小** |
| 数据模型复杂度 | 表结构复杂 | **模型更自然** |
| 长期运行风险 | 中 | **低（前提是模型合理）** |

---

# （五）、是否为业内主流、是否具备长期稳定性
### 5.1 行业实践趋势
在 **车联网 / IoT / 遥测 / 可观测领域**，主流架构趋势为：

**TSDB（原始时序） + OLAP（分析）分层架构**

+ 原始数据：InfluxDB / Prometheus / VictoriaMetrics 等 TSDB
+ 分析数据：Doris / ClickHouse / 数据湖

 **几乎没有大型系统长期用单一 OLAP 引擎承载全量原始时序数据**。

---

### 5.2 对本场景的判断
+ **InfluxDB**：
    - 是原始时序数据存储的业内主流方案之一
    - 在未来 2~3 年内仍然稳定、成熟
+ **Doris**：
    - 依然是分析层、聚合层、数仓层的主流选择
    - 不适合作为原始时序数据长期唯一存储

---

# （六）、推荐方案（结论）
### 6.1 架构结论
**不建议“二选一”替换，而建议“职责分层”。**

### 6.2 推荐分工方案
+ **InfluxDB**
    - 承载 `tbox_raw_data_compressed_new` 对应的原始数据
    - 负责历史时序查询、曲线、告警、窗口聚合
+ **Doris**
    - 承载原始数据解析、清洗、下采样后的结果
    - 用于多维分析、Join、报表、指标体系

# 二、数据流图（端到端数据流）
目标：说明 **“原始数据怎么走、解析后数据怎么走”**

---

## 1️⃣ 原始数据流（Hot Path）
```plain
车辆终端
   │
   ▼
采集网关
   │
   ▼
消息队列（Kafka）
   │
   ▼
InfluxDB
   │
   ├─► 实时车辆曲线
   ├─► 秒/分钟级聚合
   ├─► 历史轨迹回放
   └─► 告警实时判断
```

**特点：**

+ 全量写入
+ 高吞吐、低延迟
+ 查询以 **时间范围 + 聚合** 为主

---

## 2️⃣ 解析与加工数据流（Processing Path）
```plain
Kafka / InfluxDB
       │
       ▼
流式计算（Flink）
   │
   ├─ 解码（CAN / 协议）
   ├─ 清洗（异常/缺失）
   ├─ 规则计算（里程/能耗）
   └─ 下采样（秒 → 分 → 小时）
```

---

## 3️⃣ 分析数据流（Analytical Path）
```plain
流式 / 批处理结果
       │
       ▼
Doris
   │
   ├─► 车辆指标分析
   ├─► 区域 / 车型对比
   ├─► 经营报表
   ├─► 工单 / 用户 / 订单 Join
   └─► 算法特征数据
```

**特点：**

+ 数据量更可控
+ 查询复杂度高
+ SQL / BI / 多维分析友好
