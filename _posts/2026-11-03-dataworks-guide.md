## 0. 先看结论

<div class="callout callout-tip" markdown="1">
**💡 一句话理解**

DataWorks 是阿里云上的**一站式数据集成、开发、调度、治理和数据服务平台**；它负责组织数据工作流，但通常不直接承担 SQL 的计算与数据存储，实际算力和存储由 MaxCompute、Hologres、EMR、Flink、SelectDB 等引擎或数据源提供。
</div>

| 你的需求 | 推荐路径 |
| --- | --- |
| 只把少量数据从 MySQL 搬到 SelectDB | DataWorks 单表离线同步；也可评估 DataX、DTS 或 SelectDB 自带能力 |
| 每天定时把业务库接入数仓 | DataWorks 整库离线同步 + 调度 + 数据质量 |
| 秒级或分钟级同步 MySQL 变更 | DataWorks 整库实时同步（全量初始化 + CDC 增量），或 DTS/Flink CDC |
| 定期执行 SelectDB SQL、做聚合或 ETL | Data Studio 的 SelectDB 数据库节点 |
| 临时查询 SelectDB 并出图 | 数据分析 > SQL 查询 |
| 把 SelectDB 查询结果发布成 API | 数据服务，但需使用 **Doris 数据源类型**指向 SelectDB |
| 需要复杂流式计算、事件时间、状态计算 | Flink/Flink CDC 负责计算，DataWorks 可做外围编排与运维 |
| 只需要一个开源 DAG 调度器 | 评估 Airflow 或 DolphinScheduler，不必直接上完整数据治理平台 |

## 1. DataWorks 是什么

### 1.1 产品定位

DataWorks 覆盖从数据接入到数据消费的全生命周期：

1. **资源准备**：工作空间、成员权限、资源组、计算引擎、数据源。
2. **数据集成**：把业务库、消息队列、文件、对象存储等数据接入目标平台。
3. **数据建模**：数仓分层、维度建模、数据标准和指标定义。
4. **数据开发**：SQL、Python、Notebook、工作流和 DAG 编排。
5. **任务调度与运维**：周期调度、依赖、重试、补数据、告警、基线。
6. **数据治理**：数据地图、血缘、质量、安全、资产治理。
7. **数据分析与服务**：即席查询、可视化、API 发布与授权。

### 1.2 核心模块

| 模块 | 主要作用 | 典型产出 |
| --- | --- | --- |
| 管理中心 | 管理工作空间、引擎、资源组、数据源和成员 | 可运行、可隔离的基础环境 |
| 数据集成 | 离线/实时、单表/整库、全量/增量同步 | 同步任务、ODS 数据、实时写入链路 |
| Data Studio | 开发 SQL/Python、编排工作流、调试与发布 | 节点、DAG、周期任务 |
| 运维中心 | 监控实例、重跑、补数据、冻结、告警和基线 | 稳定运行的生产任务 |
| 智能数据建模 | 数仓规划、标准、维度与指标建模 | 标准化模型和指标口径 |
| 数据地图 | 元数据检索、血缘、影响分析 | 可发现、可追溯的数据资产 |
| 数据质量 | 表级/字段级规则、异常监控 | 质量告警或阻断策略 |
| 安全中心 | 分类分级、脱敏、访问控制和审计 | 合规的数据访问体系 |
| 数据分析 | SQL 即席查询、结果可视化和导出 | 查询结果、图表、报表 |
| 数据服务 | 将表或 SQL 封装为 API | 可授权、可调用的 REST API |
| 开放平台 | OpenAPI、开放事件、扩展程序等 | 自动化和企业系统集成 |

### 1.3 它解决了什么问题

| 常见痛点 | DataWorks 的解决方式 |
| --- | --- |
| 数据散落在 MySQL、Oracle、PostgreSQL、Kafka、OSS 等系统 | 用统一数据源和数据集成任务汇聚 |
| 每张表都手写脚本、配置 crontab | 用可视化任务、整库同步和统一调度替代 |
| 任务依赖复杂，失败顺序不可控 | 用 DAG、上下游依赖、重试和告警管理 |
| 开发与生产混在一起，误操作风险高 | 用标准模式工作空间和发布流程隔离环境 |
| 数据出错后才发现，报表已经扩散错误 | 用质量规则、强规则阻断和基线监控提前发现 |
| 不知道表从哪里来、被谁使用 | 用元数据、血缘和数据地图追踪 |
| 数据团队重复建设调度、权限、API 等基础设施 | 使用托管平台统一提供 |
| 敏感数据访问缺少边界 | 用 RAM、工作空间角色、分类分级和脱敏控制 |

### 1.4 它不是什么

- **不是计算引擎**：DataWorks 中的 SQL 最终由所绑定的引擎或数据库执行。
- **不是数据库**：数据仍存储在 MaxCompute、SelectDB、Hologres、OSS 等系统中。
- **不是“配置成功就绝对一致”**：数据集成官方明确为 **at-least-once**，不是端到端 exactly-once。
- **不是任何场景都必须使用**：简单同步或简单调度，引入完整平台可能增加成本和复杂度。

## 2. 优势、局限与适用边界

### 2.1 主要优势

| 优势 | 实际价值 |
| --- | --- |
| 全链路一体化 | 集成、开发、调度、质量、血缘、安全、API 在同一平台闭环 |
| 阿里云生态集成深 | 与 MaxCompute、Hologres、EMR、Flink、AnalyticDB、SelectDB 等协同顺畅 |
| 同步方案完整 | 支持离线/实时、单表/整库、全量/增量及全增量衔接 |
| 调度与运维成熟 | 周期调度、依赖、补数据、重跑、基线、告警、诊断集中管理 |
| 治理能力强 | 元数据、血缘、质量、标准和安全可贯穿研发流程 |
| 可视化与代码并存 | 向导降低入门门槛，脚本模式满足参数化和特殊配置 |
| 托管服务 | 减少自建调度、元数据和质量平台的运维工作 |

### 2.2 主要局限

| 局限 | 选型时要问的问题 |
| --- | --- |
| 云生态绑定 | 是否长期以阿里云为主？是否有多云、私有化或迁移要求？ |
| 总成本不只是软件版 | 是否已计算资源组、调度实例、质量/监控、引擎计算存储和网络费用？ |
| 平台功能多、学习成本高 | 团队是否真的需要建模、治理、服务等完整能力？ |
| 数据集成不是端到端事务系统 | 目标端是否有主键、幂等、去重和对账机制？ |
| 各数据源能力并不对称 | 当前源和目标是否支持所需的读/写、实时、整库和 DDL 能力？ |
| 自动建表不等于合理建模 | 主键、分布键、分区、字段类型是否经过业务审查？ |

<div class="callout callout-warning" markdown="1">
**⚠️ 核心选型判断**

DataWorks 更适合“已经在阿里云上，并需要完整数据研发治理闭环”的团队；如果目标只是单点同步或开源调度，应同时比较更轻量的工具。
</div>

## 3. 与其他产品对比

### 3.1 同类数据开发治理平台

| 产品 | 定位与优势 | 更适合的情况 | 主要权衡 |
| --- | --- | --- | --- |
| **DataWorks** | 阿里云一站式集成、开发、调度、治理和服务 | 阿里云引擎占比高，需要完整研发生产链路 | 云上生态绑定；成本需按全口径核算 |
| **华为云 DataArts Studio** | 数据集成、架构、开发、质量、目录、服务和安全 | 已使用华为云数据底座，或重视政企云生态 | 与华为云服务协同更深，跨云能力需实测 |
| **腾讯云 WeData** | 全链路 DataOps、协同开发、任务运维和资产治理 | 已使用腾讯云 EMR、DLC、TCHouse 等 | 与腾讯云生态绑定，具体连接器需逐项确认 |
| **Dataphin** | 强调规范定义、标准建模、指标和资产治理 | 需要强方法论、统一指标和标准化数据资产体系 | 相比 DataWorks 更偏规范建设与资产运营，实施要求更高 |
| **Apache Airflow** | 代码优先的开源工作流编排，Python 生态强 | 团队偏工程化，需要自定义 DAG 和广泛 Provider | 不是完整数据治理平台，需自行部署、运维和补齐治理能力 |
| **Apache DolphinScheduler** | 开源分布式 DAG 调度，可视化、多租户、多任务类型 | 希望自建可视化调度，保留部署控制权 | 数据集成、血缘、安全、质量等仍需组合其他系统 |

<div class="callout callout-note" markdown="1">
**📝 DataWorks 与 Dataphin 怎么区分**

可粗略理解为：DataWorks 更偏**数据工程执行平台**，Dataphin 更偏**标准化数据建设与资产治理平台**。二者存在能力重叠，也可能组合使用，最终应按建模规范、指标治理、引擎和预算做 POC，而不是只看功能清单。
</div>

### 3.2 数据同步工具不是同一类产品

| 工具 | 主要定位 | 优势 | 不适合单独承担的工作 |
| --- | --- | --- | --- |
| DataWorks 数据集成 | 同步 + 调度 + 研发治理协同 | 链路统一、任务编排和运维完整 | 不应视为所有场景下的端到端一致性或对账系统 |
| 阿里云 DTS | 数据库迁移与实时同步 | 数据库迁移、增量同步、DDL 和数据校验能力突出 | 完整数仓开发、建模和治理 |
| DataX | 开源离线异构数据同步 | 轻量、插件化、可自托管 | 实时 CDC、完整调度和数据治理 |
| Flink CDC | 实时捕获 + 流式计算 | 复杂实时转换、状态和流处理能力强 | 无需流计算的简单批量迁移 |
| SelectDB Catalog | 联邦查询外部数据源 | 适合查询或迁移部分历史数据，少一条同步链路 | 持续 CDC、整库迁移和完整任务治理 |

针对 **MySQL → 云数据库 SelectDB**，阿里云官方对比中：DTS、DataWorks、Flink CDC 均支持历史数据、增量、表结构、整库和增量 DDL；其中 DTS 支持数据校验，而 DataWorks 与 Flink CDC 在该对比表中不支持数据校验。因此使用 DataWorks 时，应自行增加行数、主键、金额等指标的对账任务。

## 4. 上手前必须理解的概念

| 概念 | 含义 | 常见误区 |
| --- | --- | --- |
| 工作空间 | 数据开发的组织与权限边界 | 把不同业务、不同密级全部混在一个空间 |
| 标准模式 | 开发环境与生产环境隔离的工作空间模式 | 直接在开发生成的配置上当生产任务使用 |
| 数据源 | 数据库或存储系统的连接配置 | 数据源创建成功就代表任务网络一定可用 |
| 资源组 | 执行同步、调度、数据服务等任务的资源 | 只关注数据库规格，忽略资源组容量和网络 |
| 计算引擎 | 真正执行 SQL/Python 等计算的系统 | 误以为 DataWorks 自己执行所有 SQL |
| 节点 | 工作流中的一个任务单元 | 节点保存后就会自动周期运行 |
| 工作流/DAG | 节点及其依赖组成的有向无环图 | 只配置时间，不配置数据依赖 |
| 周期任务 | 发布到生产后按规则生成实例的任务 | 把开发调试成功等同于生产发布成功 |
| 实例 | 某次具体运行，带业务日期和定时时间 | 重跑时忽略实例对应的数据日期 |
| 业务日期 | 本次处理的数据所属日期，日常调度通常对应运行日前一天 | 把机器当前时间当作数据时间 |
| 补数据 | 按选定业务日期重新生成并运行实例 | 在非幂等任务上直接大补数 |

## 5. 基本操作：从零跑通第一条生产链路

### 5.1 准备清单

- [ ] 明确源端、目标端、同步范围、时效要求和负责人。
- [ ] 创建或选择 DataWorks 工作空间；生产场景优先评估标准模式。
- [ ] 准备 Serverless 资源组，并明确其 VPC、EIP 和可用 CU。
- [ ] 如需 SQL 开发，绑定对应计算引擎或准备数据库节点数据源。
- [ ] 为源端和目标端创建专用账号，遵循最小权限。
- [ ] 明确开发/生产数据源是否隔离。
- [ ] 准备告警联系人、数据质量规则和对账方式。

### 5.2 第一步：配置数据源与网络

通用路径：**管理中心 → 数据源 → 新增数据源**。

1. 添加源端数据源，例如 MySQL。
2. 添加目标端数据源，例如 SelectDB、MaxCompute 或 Hologres。
3. 选择与任务匹配的资源组。
4. 执行连通性测试，分别验证资源组到源端、目标端。
5. 网络失败时按以下顺序检查：
   - VPC、路由、专线或云企业网是否连通；
   - 安全组和防火墙是否放行端口；
   - 数据库白名单是否包含资源组出口 IP/EIP；
   - 域名解析、JDBC 地址、端口和数据库名是否正确；
   - 账号是否有登录及目标对象权限。

<div class="callout callout-warning" markdown="1">
**⚠️ 公网不是默认最佳方案**

生产环境优先使用私网。公网不仅暴露面更大，还要管理 EIP、白名单和可能的流量费用。
</div>

### 5.3 第二步：创建离线同步任务

1. 在数据集成或 Data Studio 中创建离线同步任务。
2. 选择 Reader（来源）与 Writer（去向）。
3. 选择源表、目标表或目标分区。
4. 配置字段映射，逐列核对名称、顺序、类型和精度。
5. 按需配置 `where`、增量字段、切分键、并发和限速。
6. 配置写前/写后 SQL 时，重点检查删除、清空和覆盖风险。
7. 使用小数据量试跑，检查脏数据、行数和抽样内容。
8. 保存、提交、发布到生产，再配置周期调度与告警。

### 5.4 第三步：创建 SQL 节点并加入 DAG

1. 在 Data Studio 中创建工作流。
2. 新建对应引擎或数据库节点，例如 SelectDB 数据库节点。
3. 编写 SQL，先在开发环境调试。
4. 配置调度周期、定时时间、上游依赖、重试和调度参数。
5. 保存并提交，通过发布流程进入生产。
6. 在运维中心确认周期任务及实例是否按预期生成。

### 5.5 第四步：生产运维

- 查看实例状态、日志、运行时长和上下游依赖。
- 对失败实例先定位原因，再决定重跑、补数据或其他操作。
- 对核心链路配置告警与基线，关注“最终产出是否及时”，而不仅是单节点是否成功。
- 为目标表配置行数、非空、唯一性、值域和波动等质量规则。
- 变更前先查血缘和下游影响，避免只修复上游却破坏报表。

## 6. 如何接入 SelectDB

### 6.1 四种场景与数据源类型

| DataWorks 模块 | 对 SelectDB 的用途 | 应选数据源类型 |
| --- | --- | --- |
| 数据集成 | 离线单表/整库同步；在支持的实时方案中作为目标端 | **SelectDB** |
| 数据开发 | 创建数据库节点，开发并调度 SelectDB SQL | **SelectDB** |
| 数据分析 | 即席 SQL、图表和结果导出 | **SelectDB** |
| 数据服务 | 将 SelectDB 表或 SQL 发布为 API | **Doris**，单独配置并指向 SelectDB |

<div class="callout callout-warning" markdown="1">
**⚠️ 最容易踩的坑**

数据服务当前没有原生 SelectDB 数据源入口。前三个模块使用的 SelectDB 数据源，不能替代数据服务中单独注册的 Doris 数据源。
</div>

### 6.2 准备 SelectDB 连接信息

在 SelectDB 控制台的实例详情或连接信息页面获取：

| 配置项 | 填写方式 |
| --- | --- |
| MySQL/JDBC 连接地址 | `jdbc:mysql://<VPC或公网地址>:<MySQL端口>/<数据库名>` |
| MySQL 协议端口 | 常见为 `9030`，以实例实际信息为准 |
| HTTP 连接地址 | `<VPC或公网地址>:<HTTP端口>`，用于数据写入；常见 HTTP 端口为 `8080`，不要脱离实例信息硬编码 |
| 用户名/密码 | 建议为 DataWorks 建专用账号，并只授予所需库表权限 |
| 网络 | 私网优先；公网需将资源组 EIP 加入 SelectDB 白名单 |

配置后必须选择实际运行任务的资源组做连通性测试。仅在本地电脑能连接 SelectDB，并不能证明 DataWorks 资源组也能连接。

### 6.3 版本与字段限制

截至官方 SelectDB 数据源文档 2026-10-09 更新：

- SelectDB Writer 使用 MySQL Driver 5.1.47。
- 文档列出的标准 SelectDB 版本为 2.2.31、2.2.22。
- 文档列出的阿里云 SelectDB 版本为 2.4、3.0、4.0。
- 不支持写入 `BITMAP`、`HLL`、`QUANTILE_STATE` 类型字段。
- 其他类型是否可写，应以当前数据源文档和实际版本测试为准。

<div class="callout callout-note" markdown="1">
**📝 版本核验原则**

控制台显示的兼容版本、MySQL 协议版本和 SelectDB 产品内核版本可能不是同一概念。不要只凭一个版本号判断兼容性，应结合官方支持清单和 POC 写入测试。
</div>

### 6.4 MySQL 单表离线同步到 SelectDB

1. 分别创建 MySQL 与 SelectDB 数据源。
2. 在 Data Studio 创建离线同步任务。
3. Reader 选择 MySQL，配置源表、列和过滤条件。
4. Writer 选择 SelectDB，配置目标表和字段映射。
5. 检查目标表模型：
   - 需要按主键更新或去重时，通常采用 **Unique Key** 表；
   - 只追加明细时可评估 Duplicate 表，但必须自行处理重复风险；
   - 主键、分布键和分桶应结合业务查询与数据分布设计。
6. 配置批次、重试、并发和脏数据阈值。
7. 先运行小规模任务，核对源目行数、主键唯一性、空值和抽样数据。
8. 发布生产并配置调度、依赖、质量和告警。

### 6.5 MySQL 整库实时同步到 SelectDB

适用于“历史全量初始化 + 持续 CDC 增量”的场景。

**前置条件**：

- MySQL 已开启 Binlog，并满足对应格式、保留时间和 CDC 权限要求。
- 资源组到 MySQL、SelectDB 两端网络均连通。
- 已创建 MySQL 和 SelectDB 数据源。
- 源表主键与目标表主键策略已经审查。
- 已评估 DDL 变更、Binlog 清理、源库压力和断点恢复方案。

**配置步骤**：

1. 新建同步任务，来源选择 MySQL，去向选择 SelectDB。
2. 同步类型选择**整库实时**，同步模式选择**全量初始化 + 增量同步**。
3. 选择 Serverless 资源组、任务 CU、源数据源和目标数据源，测试连通性。
4. 勾选需要同步的库表，或使用过滤规则选择。
5. 配置目标库名、表名映射，刷新映射并检查自动建表结果。
6. 明确目标表主键。官方说明中，SelectDB 目标表主键用于同步写入时去重，默认沿用源表主键，因此源表主键设计非常关键。
7. 检查字段类型映射；如需附加字段，在目标表待创建阶段配置字段与赋值。
8. 配置 DDL 处理策略。对新增列、删列、改类型等操作不要盲目全部自动执行。
9. 配置读端连接数、写端并发、缓冲区、告警和资源策略。
10. 启动后分别观察全量阶段与增量阶段，检查延迟、失败记录、DDL 日志和业务对账。

### 6.6 调度 SelectDB SQL

1. 在 Data Studio 创建**数据库节点**。
2. 选择 SelectDB 类型和已注册数据源。
3. 编写 SQL，并绑定 Serverless 资源组调试。
4. 将同步任务作为上游，将聚合 SQL 作为下游，形成明确依赖。
5. 配置业务日期参数、调度周期、重试和超时。
6. 发布到生产，在运维中心验证实例。
7. 为结果表增加数据质量与对账规则。

### 6.7 即席分析与发布 API

**数据分析**：

1. 进入“数据分析 → SQL 查询”。
2. 新建 SQL 文件。
3. 在运行配置中选择 SelectDB 类型和数据源。
4. 执行 SQL，查看结果、图表或导出。

**数据服务**：

1. 新增 Doris 数据源，主机、端口、数据库、账号均指向 SelectDB。
2. FE endpoint 填 SelectDB 的 HTTP 地址和端口。
3. 在数据服务中通过向导或脚本模式创建 API。
4. 配置请求参数、返回字段、分页和访问控制。
5. 测试后发布，并只授权给需要的应用。

### 6.8 SelectDB Writer 脚本片段

以下仅展示 Writer 片段，**不是完整可运行作业**。优先由向导生成配置，再进入脚本模式调整；不要把真实密码写进笔记或代码仓库。

```json
{
  "stepType": "selectdb",
  "parameter": {
    "datasource": "selectdb_datasource",
    "table": "selectdb_table_name",
    "column": ["id", "biz_date", "amount"],
    "preSql": [],
    "postSql": [],
    "maxBatchRows": 500000,
    "batchSize": 94371840,
    "maxRetries": 3,
    "loadProps": {
      "format": "json",
      "strip_outer_array": true
    }
  },
  "name": "Writer",
  "category": "writer"
}
```

| 参数 | 作用 |
| --- | --- |
| `datasource` | DataWorks 中已注册的 SelectDB 数据源名 |
| `table` | 目标表 |
| `column` | 写入列；顺序必须与 Reader 输出对应 |
| `preSql` / `postSql` | 同步前后执行的 SQL，需防范清空、覆盖等副作用 |
| `maxBatchRows` / `batchSize` | 控制批次行数和字节数，达到任一阈值即提交批次 |
| `maxRetries` | 单批导入失败重试次数 |
| `loadProps` | 导入格式及分隔符等参数 |

## 7. 如何同步不同数据库的数据

### 7.1 先选同步方案，再配任务

| 方案 | 时效 | 适合场景 | 核心前提 |
| --- | --- | --- | --- |
| 单表离线 | T+1 或周期 | 少量核心表、精细字段映射和过滤 | 增量同步需可靠增量字段 |
| 分库分表离线 | T+1 或周期 | 多张同构表合并到目标表 | 表结构和路由规则清晰 |
| 整库离线 | 一次性或周期 | 大量表入仓、迁移、ODS 建设 | 库表映射和自动建表规则需审查 |
| 单表实时 | 秒级到分钟级 | 核心表 CDC、实时转换 | 源端支持 CDC 或为消息队列 |
| 整库实时 | 秒级到分钟级 | 实时数仓、整库全量 + 增量 | CDC 权限、日志保留、主键和 DDL 策略 |
| 整库全增量 | 首次全量，后续按方案增量 | 减少全量与增量两套任务的衔接工作 | 具体源目组合必须在支持矩阵中 |

### 7.2 常见链路建议

| 来源 → 目标 | 建议 |
| --- | --- |
| MySQL/PostgreSQL → SelectDB | 离线可用单表或整库；实时需按当前整库实时支持矩阵选择 |
| MySQL/Oracle/PolarDB/PostgreSQL → SelectDB 实时 | 官方整库实时能力页列出相关链路，但仍需逐项验证版本、CDC、DDL 和字段类型 |
| SQL Server/Oracle/DB2 等 → MaxCompute/Hologres/OSS | 先做数据源读写能力核验，再选单表或整库离线 |
| Kafka → SelectDB/实时数仓 | 若需复杂流处理优先 Flink；简单入仓再评估 DataWorks 或 Kafka Connector |
| 分库分表 MySQL → 单表 | 使用分库分表方案，保留来源库表字段，避免合并后无法追溯 |
| SelectDB → 其他存储 | 使用 SelectDB Reader 前先确认目标 Writer 和同步方案支持情况 |

<div class="callout callout-warning" markdown="1">
**⚠️ 不要凭“数据源在列表中”推断所有链路都支持**

支持 Reader 不等于支持 Writer；支持离线不等于支持实时；支持单表不等于支持整库；支持整库也不等于支持所有 DDL。最终必须查“支持的数据源及同步方案”矩阵并做 POC。
</div>

### 7.3 离线增量的正确做法

离线增量通常依赖 `gmt_modified`、更新时间或自增 ID。推荐使用半开区间：

```sql
WHERE update_time >= '${start_time}'
  AND update_time < '${end_time}'
```

其中参数名和格式仅为示意，应在 DataWorks 调度参数中定义并验证替换结果。

必须同时处理：

- **晚到数据**：数据更新时间落在上一窗口，但下一窗口才可见。
- **重叠窗口**：可适当回扫，但必须依赖目标主键幂等去重。
- **更新与删除**：仅按创建时间同步会漏更新；逻辑删除需同步删除标记。
- **时钟与精度**：确认时区、秒/毫秒精度和边界值。
- **无可靠增量字段**：不要盲目做“增量”，应改全量、CDC 或先改造源表。

### 7.4 实时 CDC 的正确做法

- MySQL：检查 Binlog 开关、格式、保留周期、账号权限和源库压力。
- PostgreSQL：检查 WAL/逻辑复制相关配置与权限。
- Oracle：检查日志、补充日志和 CDC 所需权限。
- 评估全量初始化期间持续产生的增量如何衔接。
- 监控业务延迟，而不仅是任务进程是否存活。
- 明确 DDL 是自动同步、忽略还是停止任务等待人工处理。
- 断点恢复后执行对账，不能只以“任务恢复运行”作为完成标准。

### 7.5 同步后的数据校验

DataWorks 任务成功不代表业务数据完全一致，至少增加以下校验：

| 校验 | 示例 |
| --- | --- |
| 行数 | 按业务日期、分区或主键范围比较源目行数 |
| 唯一性 | 目标业务主键是否存在重复 |
| 汇总值 | 金额、数量等 SUM 是否一致或在容差内 |
| 空值与异常值 | 关键字段 NULL、非法枚举、异常负数 |
| 最大水位 | 源目最大更新时间/日志位点是否合理 |
| 删除一致性 | 逻辑删除与物理删除是否正确传导 |
| 抽样核对 | 对高价值主键逐字段抽样比对 |

## 8. 高级操作与生产化能力

### 8.1 调度参数与业务日期

| 参数/表达式 | 含义 |
| --- | --- |
| `$bizdate` | 业务日期，格式 `yyyymmdd`；日常调度通常对应运行日前一天 |
| `$cyctime` | 实例定时时间，格式 `yyyymmddhh24miss` |
| `${yyyymmdd}` | 基于业务日期的自定义时间表达式 |
| `$[yyyymmddhh24miss]` | 基于定时时间的自定义时间表达式 |

关键规则：

- `${...}` 主要围绕**业务日期**，`$[...]` 主要围绕**定时时间**，不要混用。
- 参数替换值在实例生成时确定，与实例稍后实际启动时间无关。
- 发布前分别预览正常调度与补数据时的参数值。
- SQL 必须按业务日期处理数据，不要直接在代码里取机器当前日期代替业务日期。

### 8.2 补数据与幂等设计

补数据前回答四个问题：

1. 同一业务日期重复执行会不会产生重复行？
2. 写入是分区覆盖、主键 Upsert，还是单纯 Append？
3. 下游是否会重复触发，是否也需补跑？
4. 补数范围会不会挤占正常生产资源？

优先采用“按分区覆盖”或“业务主键 + 幂等写入”，避免依赖人工删表重跑。

### 8.3 依赖、跨周期和控制节点

- 用真实数据产出关系配置上下游依赖，不要只按执行时间串联。
- 小时任务等待天任务、当天实例等待上一周期实例等场景，应评估跨周期或自依赖。
- 分支、归并、循环等控制节点可表达复杂流程，但应尽量保持 DAG 可观察、可补数。
- 下游只依赖某几张表时，评估表级子任务依赖，避免等待无关表全部完成。

### 8.4 数据质量、基线和告警

- **质量规则**：行数、非空、唯一、值域、波动、汇总指标等。
- **强规则**：适合阻断错误继续向下游扩散；启用前需验证误报成本。
- **弱规则**：用于告警和观察，不直接阻断。
- **智能基线**：围绕最终关键产出设置，关注整条链路是否可能破线。
- **告警分级**：核心生产、普通任务、测试任务使用不同接收人与升级策略。

### 8.5 血缘、变更与发布

- 变更表结构或核心 SQL 前，先查下游血缘和 API/报表影响。
- 使用标准模式和发布流程隔离开发生产。
- 结合版本管理、代码评审、Git/OpenAPI 等能力时，先确认当前软件版本是否支持。
- 自动建表、自动 DDL、自动发布都应有人工审查边界。

### 8.6 性能调优顺序

| 层面 | 调优动作 |
| --- | --- |
| 同步范围 | 只选必要库表和列，离线优先增量，避免无意义全量 |
| 源端读取 | 过滤字段走索引；合理选择切分键；控制最大连接数 |
| 任务并发 | 根据源库承压、目标写入和资源组 CU 逐步增加，不一次拉满 |
| 写入批次 | 调整批次行数、字节数和刷新间隔，避免过小批次造成高频写入 |
| 目标表 | 优化主键、分布键、分桶、分区及字段类型 |
| 资源组 | 观察 CU、排队和内存，区分资源不足与配置不合理 |
| 调度安排 | 大表与整库任务错峰，避免与业务高峰重叠 |

### 8.7 权限与安全

- 数据源使用专用账号，禁止在笔记、脚本或 Git 中保存明文密码。
- RAM、工作空间角色、数据库账号分别做最小授权。
- 开发和生产使用不同数据源、不同账号和不同权限。
- 敏感字段同步前确认是否需要脱敏、列裁剪或禁止接入。
- 数据服务 API 配置认证、授权、分页、限流和审计。
- 定期清理不再使用的数据源和授权，但变更前先查依赖。

## 9. 高频注意事项与排障

| 现象 | 优先检查 | 处理建议 |
| --- | --- | --- |
| 数据源连通性失败 | VPC、路由、安全组、白名单、EIP、端口 | 用实际资源组测试，不要只在本机测试 |
| MySQL 实时任务无增量 | Binlog、CDC 权限、日志保留、表选择 | 检查全量到增量衔接和位点 |
| 同步后重复数据 | 任务重跑、目标表模型、主键 | 使用主键/Upsert/分区覆盖等幂等方案 |
| 字段转换失败 | 源目类型、空值、时间格式、精度 | 修正映射；不要为完成任务无限放大脏数据阈值 |
| 任务失败后数据少一半 | 已写批次、目标事务能力 | 数据集成本身不提供整体事务；修复后按幂等方式重跑并对账 |
| 实时延迟持续升高 | 源端压力、目标写入、CU、DDL、热点 | 分别观察读、写、队列和资源，不盲目只加 CU |
| 调度日期错误 | 业务日期与定时时间混用 | 预览参数替换，检查补数据值 |
| 修改字段后实时任务失败 | DDL 策略和目标表结构 | 在测试环境演练 DDL，再决定自动或人工处理 |
| SelectDB 写入失败 | HTTP 地址、账号权限、批次、字段类型 | 同时检查 MySQL 协议连接与 HTTP 写入链路 |
| 数据服务找不到 SelectDB | 数据源类型 | 数据服务使用 Doris 数据源指向 SelectDB |
| 任务成功但报表错误 | 业务对账、质量规则、迟到数据 | 增加行数、汇总值、水位和抽样校验 |

<div class="callout callout-warning" markdown="1">
**⚠️ 脏数据与事务**

官方说明：因脏数据导致任务失败时，已成功写入的数据不会由数据集成统一回滚；批量异常时能否回滚取决于目标端能力。生产任务必须按“可能部分写入”设计恢复方案。
</div>

## 10. 成本与版本选择

DataWorks 总成本应至少拆成：

1. **软件版本费**：基础版、标准版、专业版、企业版及增值模块。
2. **资源组费**：Serverless 按量或包年包月等。
3. **调度实例费**：生产周期任务产生的调度费用。
4. **其他功能费**：数据质量、智能监控、Data Agent 等按规则计费。
5. **底层引擎与存储费**：MaxCompute、Hologres、SelectDB、OSS 等独立账单。
6. **网络与外围费用**：EIP、公网流量、专线、云企业网等。

<div class="callout callout-tip" markdown="1">
**💡 控制成本的建议**

学习和 POC 可从基础能力与小规模按量资源开始；生产环境再按质量、安全、基线、开放能力等真实需求选择版本。不要把“软件版价格”当作整个数据平台的总成本。
</div>

## 11. 推荐落地顺序

### 阶段一：验证连通与同步

- 建一个测试工作空间和专用账号。
- 打通 MySQL 与 SelectDB 数据源。
- 选一张有主键的小表跑通离线同步。
- 验证重复执行、字段映射、空值、更新和删除。

### 阶段二：验证生产调度

- 建“同步 → SQL 聚合 → 质量校验”的 DAG。
- 配置业务日期、依赖、重试和告警。
- 演练失败重跑与补数据。
- 做源目行数、主键、汇总值对账。

### 阶段三：验证实时与变更

- 小范围开启整库实时或单表实时。
- 演练 Binlog 中断、任务重启、DDL、源库压力和延迟告警。
- 明确回滚、补数、灾备和负责人。

### 阶段四：再扩大范围

- 通过 POC 后再扩大表数量和 CU。
- 建立命名、权限、发布、质量和成本规范。
- 定期复核数据源支持矩阵与官方文档变化。
